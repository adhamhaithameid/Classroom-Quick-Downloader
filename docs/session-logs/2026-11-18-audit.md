## What could break

- D1: the Classroom button now shows success only at real completion —
  perceived latency grows to true download time. Any content script or e2e
  that relied on the early success flips later. Content scripts are
  another chat's lane; they were not verified.
- D2/D3: the stall deadline now depends on delta events. A transfer that
  emits no deltas for 150 s is cancelled (intended, but new). Queue waits
  never time out; the 10 min TTL sweep is the only bound for a stuck queue.
- D4: late start callbacks for cancelled/reaped pendings now cancel the
  browser download. The `interrupted` delta lands on an unregistered
  pending and is ignored — no double status expected.
- D5: the page now receives `cancelled` even when it originated the cancel;
  the content terminal-state machine must treat it as idempotent.
- D6: re-queued requests start after a worker restart (new post-update
  activity). History rows for completed-while-asleep downloads overcount
  duration (bounded by the 10 min reconcile TTL).
- D7: a user cannot start a second concurrent transfer of the same Drive
  file; the refusal message is `That file is already downloading.`
- D8: Chromium's uniquified wire names (`file (1).pdf`) may produce
  suffixed suggestions on re-download.
- D9: bridge requesters now receive `status: 'cancelled'`;
  `AcquireOutcomeStatus` already declares it, but page-side handling should
  be confirmed by the bridge/page owners.
