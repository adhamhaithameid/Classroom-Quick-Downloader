## 2024-05-28 — Debounced `handleMutations` in V2 Engine
**Finding:** The `handleMutations` method in `EngineV2` was calling `fullScan()` immediately upon detecting a relevant mutation. While `fullScan()` itself is somewhat optimized through fingerprinting, calling it synchronously on every relevant mutation in an SPA like Google Classroom is incredibly wasteful. The `MutationObserver` inside `Orchestrator` is not debounced and feeds mutations directly to engines, meaning during rapid DOM changes (like initial load or scrolling), `fullScan()` could be invoked hundreds of times per second unnecessarily.
**Action:** Added a `mutationDebounceTimer` property to `EngineV2`. In `handleMutations`, if a rescan is needed, the timer is reset. The timeout uses `this.budgetController.getDebounceMs()` to determine the delay. This perfectly solves the "undebounced observer" anti-pattern specifically mentioned in my instructions and gracefully scales with the extension's performance budget. The timer is safely cleared in the engine's `destroy()` lifecycle method.
**Learning:** `Orchestrator` manages the actual `MutationObserver` but passes raw mutation arrays straight to engines. If engines run heavy synchronous code like `fullScan()` without their own debouncing mechanism, they will tank page performance during rapid mutation streams. Always debounce heavy synchronous engine handlers!
